# Viewing Application Logs in Grafana

The project uses **Pino → Docker stdout → Grafana Alloy → Loki → Grafana** for centralized log collection and visualization.

```text
Node.js Application
        |
        | Pino
        v
     stdout
        |
        v
   Grafana Alloy
        |
        v
       Loki
        |
        v
     Grafana
        |
        v
   Explore → Loki
```

---

## 1. Start the Observability Stack

From the project root:

```powershell
docker compose up -d --build
```

Check that all services are running:

```powershell
docker compose ps
```

You should see:

```text
node-observability
otel-collector
prometheus
jaeger
loki
alloy
grafana
```

---

## 2. Verify Loki

Check Loki's readiness:

```powershell
curl.exe http://localhost:3100/ready
```

Expected:

```text
ready
```

Check available labels:

```powershell
curl.exe http://localhost:3100/loki/api/v1/labels
```

Expected:

```json
{
  "status": "success",
  "data": [
    "service_name"
  ]
}
```

Check the available service names:

```powershell
curl.exe http://localhost:3100/loki/api/v1/label/service_name/values
```

Expected:

```json
{
  "status": "success",
  "data": [
    "node-observability"
  ]
}
```

---

## 3. Verify Node.js Logs

Generate an API request:

```powershell
curl.exe http://localhost:3000/users/20
```

Check the Node.js container logs:

```powershell
docker compose logs --tail 20 node-observability
```

This verifies that the application is producing logs.

The application uses Pino for structured JSON logging.

---

## 4. Verify Grafana Alloy

Alloy collects the Docker container logs and forwards them to Loki.

Check Alloy:

```powershell
docker compose logs --tail 50 alloy
```

Alloy uses the Docker socket to discover and collect container logs.

The flow is:

```text
Docker container stdout
        |
        v
Grafana Alloy
        |
        v
Loki
```

---

## 5. Connect Loki to Grafana

Open Grafana:

```text
http://localhost:3001
```

Navigate to:

```text
Connections
    ↓
Data sources
    ↓
Add data source
    ↓
Loki
```

For the Loki URL, use:

```text
http://loki:3100
```

### Important

Do **not** use:

```text
http://localhost:3100
```

Grafana is running inside a separate container. Therefore, `localhost` from the Grafana container refers to the Grafana container itself.

Docker Compose service discovery allows Grafana to access Loki using:

```text
http://loki:3100
```

Click:

**Save & test**

You should get a successful connection message.

# 6. Open Grafana Explore

Navigate to:

```text
Explore
    ↓
Select data source
    ↓
Loki
```

You can now write **LogQL** queries.

---

# 7. View All Node.js Logs

Start with:

```logql
{service_name="node-observability"}
```

This displays all logs collected for the Node.js application.

---

# 8. Show Only Client HTTP Requests

The application uses `pino-http` for HTTP request logging.

To display only HTTP request logs and exclude application logs, use:

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url != "/metrics"
| url != "/health"
```

This query:

1. Selects logs from `node-observability`
2. Parses the Pino JSON log
3. Requires `responseTime`, which identifies the HTTP request log
4. Excludes the Prometheus `/metrics` endpoint
5. Excludes the `/health` endpoint

The result contains requests such as:

```text
GET /users/20
GET /users/40
GET /users/51
```

# 9. Generate Test Requests

Generate a successful request:

```powershell
curl.exe http://localhost:3000/users/20
```

Generate another successful request:

```powershell
curl.exe http://localhost:3000/users/25
```

Generate an intentional `400` request:

```powershell
curl.exe http://localhost:3000/users/40
```

Because IDs from `30` through `50` are intentionally configured to fail, `/users/40` returns HTTP `400`.

---

# 10. View HTTP Request Logs

Run the following LogQL query in Grafana:

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url != "/metrics"
| url != "/health"
```

You should see the requests generated by your browser, Postman, curl, etc.

For example:

```text
GET /users/20
GET /users/25
GET /users/40
```

Application messages such as:

```text
Fetching user
Invalid user ID
Creating get-user span
Span created
Span ended
```

are excluded because they do not contain the HTTP request-specific `responseTime` field.

---

# 11. Filter HTTP 400 Requests

To see only HTTP `400` requests:

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url != "/metrics"
| url != "/health"
| statusCode = 400
```

This is useful for demonstrating application errors.

---

# 12. Filter User API Requests

To show only `/users` requests:

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url =~ "^/users"
```

---

# 13. Search for a Specific User Request

For example:

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url = "/users/40"
```

# 14. Trace Correlation

Each HTTP request is associated with an OpenTelemetry trace.

The Pino logger adds:

```text
traceId
spanId
```

to logs.

First find an HTTP request in Grafana.

Then copy its:

```text
traceId
```

Search for the complete trace:

```logql
{service_name="node-observability"}
| json
| traceId = "YOUR_TRACE_ID"
```

This allows you to find all logs associated with the same trace.

You can then use the `traceId` to locate the corresponding trace in Jaeger.

```text
Grafana
   |
   | LogQL
   v
Loki
   |
   | traceId
   v
Jaeger
   |
   v
Distributed Trace
```

# 15. Useful LogQL Queries

### All application logs

```logql
{service_name="node-observability"}
```

### Only HTTP requests

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url != "/metrics"
| url != "/health"
```

### Only HTTP 400 errors

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url != "/metrics"
| url != "/health"
| statusCode = 400
```

### Only `/users` requests

```logql
{service_name="node-observability"}
| json
| responseTime != ""
| url =~ "^/users"
```

### Search for an error message

```logql
{service_name="node-observability"} |= "Invalid user ID"
```

### Logs for a specific trace

```logql
{service_name="node-observability"}
| json
| traceId = "YOUR_TRACE_ID"
```

# 16. Direct Loki Verification

Grafana is not required to verify that Loki has received logs.

Query Loki directly:

```powershell
curl.exe "http://localhost:3100/loki/api/v1/query_range?query=%7Bservice_name%3D%22node-observability%22%7D&limit=20"
```

For HTTP requests:

```powershell
curl.exe "http://localhost:3100/loki/api/v1/query_range?query=%7Bservice_name%3D%22node-observability%22%7D%7C%20json%7C%20responseTime%20!%3D%20%22%22&limit=20"
```

Use the direct Loki API when troubleshooting whether logs are reaching Loki.
